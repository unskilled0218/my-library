## Files and setup

My Library includes baseline-derived `scripts/release.sh`, `scripts/release-common.sh`, `scripts/release-data.py` with [documented local adaptations](release-adaptations.md), consumer `scripts/release.json`, an application `Dockerfile`, `.dockerignore`, root `VERSION`, and committed Markdown release notes. `.template-operation.lock`, `.release-template/`, and `.template-transaction/` are ignored. Commit the complete setup and push its clean `main` before publication. No managed installation or network self-update runs during release. See [provenance and readiness](publish-a-release.md).

Follow the [release process](release-process.md) for the ordered readiness checklist, progress expectations, and troubleshooting. Tool availability is checked before builder access; `--validate` does not prove server connectivity or publication permissions.

The application Dockerfile runs the standalone Next.js server, Prisma migrations, and installed Chromium as a non-root user. This checkout targets only `dev/my-library` and `git.lan/dev/my-library`. Review these settings and effective Git remotes before publication; no template Hello World image is used.

## Settings

`scripts/release.json` has exactly schema 1 fields: `schema`, credential-free HTTPS `gitea` origin, `repository` as `owner/repository`, full `image` as `host/owner/name`, `username`, `token_file`, relative regular-file `notes`, and `platforms` as `["linux/amd64", "linux/arm64"]`. The host/owner scopes must agree. Simple lower-case repository/image names are supported; nested image namespaces are not. Unknown/duplicate fields, controls, traversal, symlinks in active paths, and inconsistent scopes are refused. Configuration is JSON data, never executable shell code.

Root `VERSION` supplies `MAJOR.MINOR.PATCH` without leading zeroes, at most 16 characters; the Git tag is derived as `v<version>`. Notes must be a committed UTF-8 regular blob, at most 64 KiB, beginning `# Release v<version>` followed by project updates. Narrow newline normalization is applied; the resulting text is the entire public release body. Image/digest identity lives separately in a distinct annotated Git tag.

`./scripts/release.sh --validate` checks local settings/version/paths without reading credentials, creating state, contacting services, or invoking Docker. `--help` needs only Bash. No arguments selects publication; other arguments, including old subcommands and configuration flags, are refused with current usage before credentials or external effects. Invocation from another directory still selects the root containing the script. The old Python CLI, examples, and installer/updater are not shipped. Historical transactions require their preserved original checkout/pin; old installation/checkpoint markers remain refusals, never migration authority.

## Credentials and prerequisites

Use a non-symlink, user-owned, readable mode-0600 or mode-0400 token file outside the project. Default: `~/.config/git/token`; `GIT_TOKEN` optionally overrides the file path, never the token value. Optional `GIT_USERNAME` overrides the configured login. No inline environment assignment is needed for the configured default. Provision the token privately, never in Git, `.env`, shell history, command arguments, or this documentation. It needs repository and package read/write permissions, including release creation and write access to the repository's packages unit; independent Git authentication is also required. Token scopes alone do not grant access to resources the account cannot manage.

The server must support the Gitea repository GET, container package-version GET with an explicit nullable `repository` field, and package-link POST documented in [package association](bash-publication.md#package-association). New link writes additionally require `GET /api/v1/version` to report stable `1.25.x` or exact stable `28.2.0`. Server-side refusal to replace existing links was checked in v1.25.0 and pinned v28.2.0 source; null repository responses can hide inaccessible links. Other versions (including `28.2.1`), development builds, suffixes, and failed version reads cannot authorize writes. Existing correct links remain read-only without a version check. No deployed server is certified by these source checks. Existing credentials are reused; no additional settings or flags are needed. The configured image name may differ from the repository name. Operators must exclude other package-association writers, including UI actions and in-flight requests, through completion; the checkout lock is not a distributed lock. On 28.2.0, linking requires package-write access and target repository package-unit write permission, in addition to the API token scopes and read access used for identity evidence; a version match does not grant permissions.

The release runner requires Bash, Python 3.11+ standard library, Git, curl, Docker Buildx, and standard Linux utilities. The runner has no jq, Node, pip dependency, or separate engine package; application checks separately require Node/npm. Python handles strict JSON/UTF-8, hashing, bounded pipes, locks, private auth preparation, and source archive validation. Bash owns the publication sequence. Root `VERSION` is authoritative; npm package metadata must match and is checked by the consumer test suite, not by `--validate`.

Keep HTTPS trust enabled for Git/curl/Docker. Authenticated curl requests disable ambient curl configuration and do not follow redirects; registry bearer-token realms must be same-origin. Docker uses a private minimal auth directory with no inherited credential helpers, preserving the selected context and builder connection. Normal exit/failure/signals remove only the run-owned private temporary directory. SIGKILL cannot run cleanup; inspect any leftover private temporary directories securely, not with broad cache deletion.

Auth isolation captures the original connection selection before replacing `DOCKER_CONFIG`. A host-only selection keeps `DOCKER_HOST`, `DOCKER_TLS_VERIFY`, and `DOCKER_CERT_PATH` without newly exporting a default context over it; empty context values also remain unselected. An explicitly selected context retains its precedence, including explicit `default`. A non-default context selected through the original config is carried into the private environment with its required endpoint/TLS metadata, never with the original registry auth/helper inventory. An unset or empty `DOCKER_CONFIG` uses the caller's home Docker directory. Explicit buildx state paths are retained; default buildx state remains rooted in the original Docker directory, not the temporary auth directory. Relative connection paths retain the caller's working-directory semantics.

Private auth preserves ordered `cliPluginsExtraDirs` and only the original config-local `docker-buildx` candidate, referenced through an absolute symlink. Original Docker JSON is strictly parsed within 1 MiB; invalid discovery fields and unusable selected candidates are refused without exposing system fallback. Missing original config remains valid. No original registry auth/helper inventory is copied. Native daemon-free marker-plugin tests exercise this discovery contract; fake connection tests remain separate and do not certify real daemon routing or TLS. Executable directories remain trusted operator inputs. See [adaptations and review status](release-adaptations.md) and remaining [known limits](bash-publication.md#known-limits).

The builder must advertise both platforms before remote Git/auth/build operations. This does not prove emulated runtime execution. Host preparation needs separate administrator action; the release command never installs privileged emulation support.
