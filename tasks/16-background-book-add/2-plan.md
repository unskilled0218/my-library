## scope

Make Kyobo book additions continue during client-side navigation within the app. Users can search, open libraries, and submit another book while earlier additions run. A persistent, non-blocking status panel shows each addition's pending, success, existing-book, or failure state and supports recovery without losing submitted options.

Use the existing Next.js server, import logic, and root layout. This task covers Kyobo additions from `KyoboAddBookForm`, client-side header and library search submission, and reconciliation of an uncertain save with an existing book; manual entry keeps its current behavior. Background work lasts for the current open app session; durable jobs across explicit browser reloads, tab closure, or server restarts are outside this task. Ordinary app search must preserve that session rather than reload the document.

## Implementation Plan

### 1. Separate book import from navigation

- Extract the import body of `addKyoboBookAction` from `src/app/actions.ts` into a server-only module such as `src/lib/kyobo-import.ts`. Accept an authenticated user and submitted form data, and return a discriminated result: `created` or `existing`, each containing `bookId` and `libraryId`, or `error` containing a `KyoboAddError`.
- Preserve product and option validation, WRITE access checks, library-owner shelf validation, destination folder validation, authoritative Kyobo retrieval, ebook location clearing, duplicate detection, cover download and cleanup, transaction boundaries, genre updates, and audit logging.
- Return the created book ID from the transaction. Extend the existing destination-scoped duplicate query to return the authorized existing book's ID and library ID as an `existing` result, without creating a row, changing its options, or emitting a new creation audit record. Keep `q` and `source` as navigation context outside the import service; preview metadata remains display-only.
- Keep `addKyoboBookAction` as a thin compatibility wrapper that requires a user, invokes the service, revalidates affected paths after creation, and retains its current success redirect and error contract. Map `existing` back to `{ error: 'alreadyExists' }` for this wrapper. Define the richer shared result type in a client-safe module separate from the server-only import service, so the endpoint and provider can distinguish creation from an existing book without changing redirect-based callers.

### 2. Add a background request endpoint

- Add `POST /api/books/kyobo` in `src/app/api/books/kyobo/route.ts`. Use `currentUser()` to return a JSON authentication failure rather than redirecting a fetch to login, parse `FormData`, and call the shared import service.
- Restrict mutation requests to the same origin, accounting for the application's existing reverse-proxy deployment. Return typed JSON for expected errors, malformed requests, and unexpected failures; never expose an exception stack to the client.
- On `created`, revalidate `/`, `/libraries`, and the destination library, then return the created IDs. Return `existing` with its authorized IDs as a terminal, non-mutating outcome, without reporting a new save or invalidating caches for a write that did not happen. The endpoint must await the import before reporting its outcome; do not launch an untracked promise after returning a response.
- Use an ordinary client `fetch` for this endpoint, independent of the Server Action submission queue, so a slow Kyobo request does not hold up unrelated navigation or form actions. No polling, streaming, database migration, or new package is needed.

### 3. Keep background additions in the shared layout

- Add a client provider such as `src/components/book-add-provider.tsx` under `LocaleProvider` in `src/app/layout.tsx`. Mount it across page changes and scope its state to the current user ID; clear task state when the authenticated identity changes and ignore late responses from an earlier identity.
- Store a unique task ID, `saleId`, destination ID/name, a display title with a localized fallback, the originating detail URL, an immutable snapshot of submitted option values, and `pending`, `success`, `existing`, or `error` state. Store the authorized book/library IDs for terminal book outcomes and distinguish uncertain network errors from confirmed failures. Keep snapshots in memory rather than URLs or browser storage.
- Expose submission and task lookup APIs to forms. Start requests from the provider, not a page component's lifetime; unmounting the detail page or collapsing the status panel must not abort an addition.
- Atomically guard against repeated submissions for the same `saleId` and library while pending. Allow different books to run independently, including completion in a different order. Keep successful and existing-book entries guarded against immediate accidental resubmission until explicitly dismissed.
- On completion, update only the matching task. Refresh current route data after a successful save without changing the current URL or stealing focus; success links let users choose when to open the destination library or book.
- Retain failed snapshots for explicit retry and editing. Retry reconstructs the same submitted options and runs server validation again. Treat network loss as an uncertain result, show a distinct message, and never automatically retry a mutation. If a prior attempt committed but its response was lost, an explicit retry that finds the book transitions the task to terminal `existing`, stops offering retry, and exposes view/edit links. This outcome does not prove which attempt created the book and must not claim that retry options were applied.

### 4. Connect the add form and progress panel

- Change `src/components/header-search.tsx` to prevent native GET submission and call `router.push` with the submitted query and selected source, preserving the existing native GET fallback, browser validation, anonymous Kyobo-only behavior, and scanner behavior. This keeps the root provider alive while searching for the next book.
- Apply the same client-side GET submission behavior to `src/components/library-search-controls.tsx`, retaining the current pathname, submitted query/filter values, and hidden folder scope. Inspection found native GET forms in these two components; the global search page and library pages otherwise use links or Server Actions. Check those routes again during implementation and convert any additional native search/filter submissions encountered in this workflow, without changing mutation forms.
- Replace the page-bound `useActionState` submission in `src/components/kyobo-add-book-form.tsx` with provider submission. Capture enabled form values and the current search context synchronously, register the task, and return control immediately.
- Pass a display title from `src/app/search/kyobo/[saleId]/page.tsx` when available. On revisiting a detail page, show the matching task state and restore a failed submission's options when that destination is still writable; reconcile removed shelves or folders against current destination choices.
- Keep existing destination switching rules, option defaults, ebook restrictions, and localized field errors. Disable only a matching pending submission; other page controls, destinations, and books remain usable. Provide the existing back-to-results link while pending, with no completion-time redirect.
- Add a compact status trigger and expandable panel such as `src/components/book-add-status.tsx` in the shared layout. Show the active count and per-book title, destination, indeterminate activity indicator, and terminal result. Render `existing` as “already in library” with view/edit links, distinct from a newly saved book and from an error; explain that submitted retry options were not applied. Collapsing hides details but leaves the trigger available; dismissing terminal entries removes their snapshots.
- Provide retry and return-to-form controls for failed entries, book/library links for successful entries, and existing-book view/edit links without a retry control for `existing` entries. Validation failures can be corrected in the restored form; authentication failures provide a sign-in link instead of repeatedly retrying an expired session. Refresh the current route when an uncertain outcome resolves to an existing book so the previously committed save is visible without forcing navigation.
- Use a non-modal region or popover with no backdrop or focus trap, keyboard-operable controls, `aria-expanded`, polite status announcements, and failure alerts. Keep the page interactive, avoid invented percentages or import stages, and fit narrow mobile screens without horizontal overflow.
- Extend `src/lib/i18n/search.ts` with Korean and English labels for background activity, task counts, success, failure, uncertain network outcomes, existing-book outcomes, unapplied retry options, retry, edit, and panel controls. Reuse existing error translations and locale context.

- Update `src/components/header-search.test.tsx` and `src/components/library-search-controls.test.tsx` to check client-side GET submission with the actual submitted values, source rules, folder/filter preservation, and unchanged scanner behavior. Retain useful native fallback assertions rather than replacing search semantics with implementation-only checks.
- Update `src/components/kyobo-add-book-form.test.tsx` and add provider/panel tests using deferred mocked fetch responses. Verify a request finishes after the originating form unmounts, independent additions complete out of order, rapid repeated submits produce one request, identity changes hide previous task data, retries preserve options, errors remain recoverable, and completion never pushes a route. ## Acceptance Criteria

- Submitting a Kyobo book immediately shows a pending task, and the user can navigate and use other controls before retrieval finishes.
- Pending work and its status survive client-side route changes, actual header search submission, and library search/filter submission with query, source, and folder semantics preserved. Multiple different books can be added independently, and a repeated click on the same pending book/destination starts only one request.
- Every task identifies the book and destination and reaches a visible success, existing-book outcome, or actionable failure. Closing the panel does not cancel the request, and completion leaves the current page and focus in place.
- A successful addition appears in the chosen library with its selected options, authoritative metadata, and audit record. Current library data refreshes without forcing navigation.
- A failed addition retains submitted values for retry or correction after returning to its form. Authentication and uncertain network failures have clear recovery paths; requests are never retried automatically.
- If a save commits but its response is lost, explicit retry resolves to an “already in library” entry with authorized view/edit links and no retry loop. It creates no second book or creation audit and does not overwrite options or claim that retry options were applied.
- Browser navigation coverage gates the real request before forwarding or pauses metadata retrieval, uses actual app search submissions while pending, and verifies real persistence after release. A separate committed-but-lost-response case verifies existing-book reconciliation.
- The status interface works with keyboard navigation, screen-reader announcements, Korean and English locales, and mobile layouts.
- Existing permission, validation, duplicate, transaction, cover-cleanup, and manual-entry behavior continues to pass relevant checks.

## Risks And Decisions

- Background means work continues during in-app navigation and ordinary app search in the open tab. A root-layout provider plus a normal HTTP request meets that scope only when header and library GET forms use client-side navigation. Explicit browser reloads or closed tabs lose in-memory status and may leave the save outcome unknown; persistent recovery would require a separate durable-job design.
- A route handler avoids coupling slow imports to Server Action dispatch. Extracting one shared service prevents the new endpoint and compatibility action from drifting apart.
- Progress is indeterminate because the existing import function does not report stages. Pending and terminal states communicate real information without adding a streaming protocol.
- Keep server-side duplicate checks and add a per-session client guard. The existing check-before-create race across separate tabs or users remains a known limit; do not promise database-wide exactly-once delivery.
- An `existing` result reconciles a retry with a saved book without attributing its creation to a particular attempt. It neither reapplies submitted options nor supplies a general idempotency guarantee. The current WRITE access check and destination-scoped duplicate lookup must run before exposing existing IDs, and the compatibility action retains its existing duplicate-error shape.
- Retain snapshots only until terminal entries are dismissed or the user session changes. Use a fallback product label for direct detail URLs that lack preview data, and never trust that label as saved metadata.
- Browser tests must use actual header/library form submissions and client-side links when proving navigation survival; `page.goto()` reloads the document and exercises a different lifetime. Keep pending-work gates separate from response-loss simulation, retain real persistence checks, and preserve the existing disposable-database requirement and test-only fixture guards.
