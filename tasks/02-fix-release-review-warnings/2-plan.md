## Scope

Resolve all four warnings in `tasks/01-update-build-image/5-code-review.md`: the post-promotion predecessor guard, Buildx executable discovery after authentication isolation, surviving publication-test descendants after timeout, and undeclared dependence on `/tmp/opencode`. Apply minimal, explicitly documented downstream adaptations to template baseline `5b918ba0aefb9ac9643fa99976140c95d17cb3e2` rather than silently changing the upstream pin or waiving either publication warning. Add regressions and preserve all existing publication safeguards. This planning stage changes only this document; implementation, image-build troubleshooting, browser acceptance, and live publication are not performed here.

### 2. Tighten the post-promotion invariant

1. Separate alias validation before promotion from validation after successful promotion in `scripts/release.sh` and `scripts/release-common.sh`. Before promotion, continue accepting the captured predecessor or the prepared digest so staging reuse, accepted-response reconciliation, and already-prepared promotion remain supported.
2. After the explicit promotion-confirmation read proves `latest == prepared`, require only the prepared digest in the guard immediately preceding release POST. Use a clearly named phase-specific guard or explicit confirmed-promotion state; tag confirmation alone must not imply promotion confirmation. Retain fresh source, configuration, complete inventory, exact tag/peeled-commit, and absent-release checks.
3. Extend `tests/fixtures/bash_release_ports.py` with a precise injection point after confirmed promotion and before release creation. Cover predecessor restoration when an old digest existed and alias disappearance when the captured predecessor was absent. Both must return nonzero without release POST, package-link POST, repromotion, tag repush, or rollback after the injected observation.
4. Cover a newly foreign alias and failed/malformed/oversized post-promotion alias reads as fatal before later writes. Assert that the intended injection was reached, accepted tag/image evidence remains intact, no success summary is printed, and no guard recaptures the predecessor to justify continuing.
5. Keep successful fresh publication, already-prepared promotion, lost accepted promotion responses, completed read-only retries, and tag-only/release-only startup refusals passing. Do not promise atomicity against changes occurring after the final read; exclusive writers remain an operational prerequisite.

### 3. Preserve Buildx plugin discovery across authentication isolation

Preserve existing system-plugin fallback only when no higher-priority candidate exists. Do not copy or link the entire original Docker configuration or unrelated credential/plugin inventory.
3. Read original Docker JSON with an explicit byte bound and strict parsing; validate the discovery field's type and path entries without printing configuration contents. Missing original `config.json` remains valid. Invalid discovery configuration or an unusable previously selected candidate must fail closed rather than silently selecting a different plugin. Normalize relative discovery references against the original invocation context where needed; preserve precedence, not just the Buildx version string.
4. ### 4. Own and reap publication-test processes

1. Introduce a small test-only support module, such as `tests/release_test_support.py`, for publication process ownership and teardown. Replace the common `subprocess.run(..., timeout=90)` release invocation with `Popen` plus bounded `communicate`, preserving stdout/stderr capture, exit-result assertions, sentinel checks, and the existing ordinary timeout.
2. Register cleanup immediately after launch, before assertions can fail. On timeout or test interruption, send SIGTERM to the still-live lock-owner process so its existing handler forwards termination to the Bash child session. Wait for a short bounded grace period and drain output. Capture diagnostics without exposing credentials; preserve `TimeoutExpired` or an equally explicit failure rather than converting timeout into a normal release result.
3. Track fixture-owned descendant/session identities while their ancestry is still observable. If graceful termination fails, escalate only against confirmed owned survivors, checking process identity before signaling to avoid PID reuse. Account for the lock owner's separate child session and the command helper's separate process groups; killing the original parent group alone is insufficient. Reap children and close pipes before deleting fixture directories. Never use process-name matching, global `pkill`, broad `/tmp` deletion, or signals against unrelated processes.
4. Reuse the ownership helper in special progress/signal tests where appropriate, retaining their synchronization barriers and behavior assertions. Keep ownership machinery in tests unless a separately diagnosed production defect requires revising the scope; do not add test-only lifecycle controls to production scripts.
5. Add a deterministic short-timeout regression that first observes a fixture command and its descendant entering a controlled wait. After the forced timeout, assert that all recorded owned processes exited, no delayed marker or mutation occurs, the checkout lock is acquirable, and run-owned temporary paths are removed. Add an escalation case for an owned process that ignores graceful termination, plus successful/nonzero-exit cases confirming normal harness behavior. Use barriers and bounded waits instead of timing-dependent sleeps as the primary synchronization.

## Acceptance Criteria

- Post-promotion observation of the predecessor, absence, foreign state, or failed evidence stops before release/association writes. Pre-promotion predecessor acceptance and all supported retry paths remain intact; no rollback or destructive repair is introduced.
- Native Docker CLI tests demonstrate that the private-auth boundary preserves the selected Buildx implementation and search precedence. Original unrelated credentials and helpers remain excluded, and context/host/builder selection regressions pass.
- Forced publication-test timeouts terminate and reap owned descendants across session/process-group boundaries, release locks, close pipes, and clean owned paths without signaling unrelated processes. Normal successful and failed commands retain existing assertions and timeout limits.
- Release tests run with an available preferred temporary directory and with an absent preferred path, without requiring or modifying shared `/tmp/opencode` state. All existing cases remain discoverable and new regressions execute.
- Upstream baseline and local adaptations are accurately distinguished in documentation and hash assertions. Source version, npm metadata, configured notes, and operator links agree; offline validation remains credential-free and side-effect-free.
- Relevant Python, shell, native plugin-discovery, formatting, lint, type-check, unit, and application-build checks pass, or precise blockers are recorded without claiming the affected warning resolved.
- Publication remains a separate, gated activity. No source push, live publication, remote mutation, privileged preparation, unrelated-file cleanup, or image/browser acceptance claim occurs in this task.

## Risks And Decisions

- This task chooses explicit minimal downstream patches, not an unreviewed upstream upgrade. Plan/code review must assess those patches before any release-readiness decision; the prior N1/N2 warnings are not waived by planning them away.
- Docker plugin discovery is implementation-sensitive. Validate actual Docker CLI behavior, ordered extra directories, config-local candidates, and system fallback; matching version strings or fake connection tests cannot establish executable selection. If preservation cannot be demonstrated for a supported configuration, refuse it and report the limit rather than silently switching implementations.
- Referenced plugin binaries and discovery directories remain trusted operator-controlled executable inputs. Preserving discovery does not protect against their concurrent replacement or hostile filesystem changes. Do not claim binary immutability or distributed writer exclusion from local path preservation.
- Timeout teardown spans multiple sessions and process groups. Graceful forwarding is the primary path; ownership-checked escalation is a test-harness responsibility and must not become broad host process cleanup. Do not assert that this leak caused the previous unrelated intermittent failures without evidence.
- Changing protocol hashes intentionally prevents adoption of old-format identity evidence. Preserve historical checkouts; no tag rewriting, remote cleanup, or recovery migration belongs in these fixes.
- `0.7.9` is provisional source metadata. Image-build crashes, architecture-specific runtime checks, browser acceptance, authenticated remote version availability, exclusive writers, and clean already-pushed `main` remain independent publication gates after these warnings are fixed.
