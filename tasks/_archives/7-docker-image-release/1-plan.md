# Build and publish the production Docker image

## Goal

Package My Library as an immutable production image containing the Next.js standalone server, Prisma runtime and migrations, and Playwright Chromium, then publish versioned multi-platform manifests and `latest` to the self-hosted Forgejo container registry at `git.lan/dev/my-library`. Provide a production Compose deployment that preserves PostgreSQL and cover data outside the application container and a guarded release command modeled on `git.lan/dev/my-rss`.

## Confirmed baseline

- The application is Next.js 16 on Node 24 and already builds with `output: 'standalone'` in `next.config.ts`; the standalone output includes the Playwright runtime but not the Prisma CLI needed by `prisma migrate deploy`.
- `package.json` and `package-lock.json` currently identify version `0.4.1`, the repository has no Git tags, `main` tracks `ssh://git@git.lan/dev/my-library.git`, and the next release should establish one matching package, Git, Forgejo release, and Docker image version.
- The current `docker-compose.yml` is a development stack. It bind-mounts the repository, installs npm packages and Chromium on every fresh container volume, runs `next dev`, and stores PostgreSQL, covers, npm modules, and browsers in named volumes.
- Production requires `DATABASE_URL`, a `SESSION_SECRET` of at least 32 characters, and a writable `COVER_STORAGE_PATH`. Optional `ADMIN_ID` and `ADMIN_PASSWORD` must be supplied together. `ALLOWED_DEV_ORIGINS` is development-only and is not required by the production server.
- `src/instrumentation.ts` performs administrator bootstrap when the Node server starts, and `/api/health` already reports database readiness. Database migrations must complete before the server starts so bootstrap and requests never observe an old schema.
- Kyobo detail lookup launches Playwright Chromium at runtime. The browser executable and Linux libraries must be installed in the image during build; production startup must not run npm, apt, or Playwright downloads.
- The reference repository publishes `linux/amd64` and `linux/arm64` with Docker Buildx, authenticates to `git.lan` using a Forgejo token passed through stdin, retains an immutable semantic-version tag, and updates `latest` only after the versioned release succeeds.
- Docker is not installed in the current planning container, and no Forgejo write token is available. Image build, runtime smoke tests, and live publication must be performed on a release workstation with Docker Buildx and registry access; implementation must report rather than conceal any unavailable live verification.

## Image design

- Add a multi-stage `Dockerfile` based on the existing Node 24 Debian family rather than Alpine, because Prisma, Playwright Chromium, and its system dependencies must use compatible glibc binaries.
- Install dependencies reproducibly with `npm ci`, run `npm run db:generate`, and build the Next.js standalone output in a build stage. Build without copying `.env` or passing production secrets so no database URL, session secret, or administrator credential can be embedded in image layers or generated output.
- Make the Prisma CLI a production dependency because migrations are a production startup operation. Build a production dependency tree with `npm ci --omit=dev`; do not install dependencies at container startup or depend on the source-mounted development `node_modules` volume.
- Assemble only the production dependency tree, `.next/standalone`, `.next/static`, Prisma schema/migrations, package metadata, and a small entrypoint in the runtime stage. There is currently no `public/` directory; account for it only if it exists when implementation runs.
- Install the Playwright version locked by `package-lock.json`, Chromium, and its operating-system dependencies in the runtime image at build time. Set one explicit `PLAYWRIGHT_BROWSERS_PATH` and verify that the non-root runtime user can read and execute the bundled browser.
- Run as a dedicated unprivileged user, listen on `0.0.0.0:3000`, expose port 3000 as metadata, and use an exec-form entrypoint so `node server.js` receives stop signals as PID 1 after migration finishes.
- Add a startup script that runs the image-local `prisma migrate deploy` against `DATABASE_URL` and then `exec`s the standalone server. Use strict shell error handling so a failed migration prevents the application from starting; do not seed production data or run development migrations.
- Add an image health check against `http://127.0.0.1:3000/api/health` using a client already available in the selected runtime image, or implement the probe with Node so no package is installed only for health checks.
- Add OCI labels for source repository, revision, and release version through build arguments supplied by the release command. Keep labels non-sensitive and ensure the immutable image can be traced back to the exact Git commit.

## Implementation

1. Add a whitelist-oriented `.dockerignore` that admits only files needed for dependency installation, Prisma generation/migrations, and the Next.js build. Explicitly exclude `.git`, `.next`, `node_modules`, `.env*`, tasks, tests and reports, local data/covers, logs, TypeScript build info, and release output so credentials and machine state cannot enter the build context; allow `.env.example` only if documentation requires it.
2. Move `prisma` from `devDependencies` to `dependencies` in `package.json` and refresh `package-lock.json` without changing its resolved version. Keep `tsx` and the development seed outside the runtime dependency set.
3. Add the multi-stage `Dockerfile` and entrypoint described above. Copy static assets beside the standalone server, copy all migration SQL required to initialize an empty PostgreSQL database, create the cover directory with non-root ownership, and avoid retaining npm caches, compiler inputs, test tooling, or development-only packages in the final image.
4. Convert `docker-compose.yml` from the source-mounted development process to the deployable registry stack used by the reference project. Use `git.lan/dev/my-library:latest`, publish `3000:3000`, set `NODE_ENV=production`, load secrets and connection values from `.env`, set `COVER_STORAGE_PATH=/app/data/covers`, retain PostgreSQL and covers in named volumes, add `restart: unless-stopped`, preserve the healthy-database dependency, and make the app health check use `/api/health`. Remove the source, npm-module, and browser-cache volumes because code, dependencies, and Chromium belong in the image.
5. Add `scripts/release.sh` as the single maintainer entry point. It must use `set -euo pipefail`, reject positional arguments, require Docker, Buildx, Git, a clean `main` checkout, and `FORGEJO_TOKEN`, and authenticate with `docker login git.lan --password-stdin`; default `FORGEJO_USER` to `dev` without printing the token.
6. Use the exact semantic version in `package.json` as the release source, require `package-lock.json` to match it, derive `vMAJOR.MINOR.PATCH` for the Git, Forgejo, and image tag, fetch remote tags, and refuse an existing version before any push. Bump both package files from `0.4.1` to `0.5.0` for this deployment capability so the first release is `v0.5.0`, rather than restarting the established package lineage at `v0.1.0`; future releases must update the package version in a normal reviewed commit before running the helper.
7. Before publication, have the release helper run `npm ci`, `npm run format:check`, `npm run lint`, `npm run typecheck`, `npm test`, and `npm run build`. Keep browser end-to-end tests as a documented pre-release check against the disposable Compose stack because they require a migrated PostgreSQL database and running browser environment.
8. Build and push `git.lan/dev/my-library:v0.5.0` for `linux/amd64,linux/arm64` with Buildx, passing the release version, source URL, and exact revision as labels. Inspect the pushed manifest and require both target platforms before creating or moving any mutable tag.
9. Create and push the matching annotated Git tag only after the versioned image is confirmed. Create the matching non-draft Forgejo release through its API, treating an existing mismatched tag/release as an error; do not upload image archives because this task publishes through the container registry.
10. Update `git.lan/dev/my-library:latest` from the verified version manifest only after the immutable image, Git tag, and Forgejo release succeed. Never rebuild separately for `latest`, overwrite an existing semantic-version image, or update `latest` after a partial failure.
11. Update `README.md` with separate production deployment and maintainer release sections. Document Forgejo registry login, `.env` creation and secret requirements, `docker compose pull`, `docker compose up -d`, readiness checks, initial administrator setup, upgrade and PostgreSQL backup expectations, rollback limits after schema migrations, the release token's repository/package permissions, Buildx/binfmt prerequisites, and the exact release command. State that self-signed `git.lan` certificate trust belongs in the host Docker daemon/CA configuration and must not be bypassed in project scripts.
12. Update the local-development instructions now that default Compose is production-oriented: run PostgreSQL through an explicitly documented development command or profile and run the app with `npm run dev`, without silently pulling the production image or exposing production secrets to the build.

## Verification

- Run `npm run format:check`, `npm run lint`, `npm run typecheck`, `npm test`, and `npm run build` outside Docker.
- Run `bash -n` on the entrypoint and release helper. Exercise release-helper argument rejection, invalid package version, missing token/tool, wrong branch, dirty tree, package/lockfile mismatch, and existing-tag failures without pushing an image.
- Build the final image for the workstation architecture with the same build arguments used by the release helper. Inspect its labels, configured user, entrypoint, command, exposed port, health check, architecture, and layer contents; confirm `.env`, Git metadata, tests, tasks, source-only files, npm cache, and development dependencies are absent.
- Scan the image filesystem/history for representative `SESSION_SECRET`, `ADMIN_PASSWORD`, and registry token values and confirm none are present. Confirm the runtime UID is non-root and can write only the intended cover-data mount.
- Start a disposable Compose project with an empty PostgreSQL volume and cover volume. Confirm migrations initialize the schema before startup, bootstrap produces the expected one-time administrator behavior, `/api/health` becomes ready, registration/sign-in and a basic library page work, and the app survives a restart without reinstalling packages or Chromium.
- Run a Kyobo detail lookup from the built container and confirm bundled Chromium launches as the non-root user. Confirm failed database connectivity keeps the app unhealthy and a failed migration prevents the server process from starting.
- Run `npm run test:e2e` against the disposable built-image stack, including its desktop and mobile projects, then recreate the app and database containers and confirm PostgreSQL records and stored covers persist in their named volumes.
- On a Buildx workstation with AMD64/ARM64 emulation and a disposable pre-release version, push the versioned image, inspect the remote manifest for both platforms, pull by immutable tag, and run the pulled image rather than a locally cached build. Verify duplicate semantic-version publication is rejected.
- For the real `v0.5.0` release, record the source commit, package version, remote manifest digest and platforms, Git tag, Forgejo release URL, immutable image pull/start result, and `latest` digest. If Docker, credentials, certificate trust, or registry access is unavailable, do not create tags/releases or claim publication; record the exact blocked checks for an operator to complete.

## Acceptance criteria

- `git.lan/dev/my-library:v0.5.0` and `git.lan/dev/my-library:latest` resolve to the same verified multi-platform manifest containing `linux/amd64` and `linux/arm64`, and the immutable image maps to Git tag and Forgejo release `v0.5.0` on the exact release commit.
- A fresh production Compose deployment needs only Docker, the Compose file, registry access when private, and runtime `.env` values; it does not clone source, bind-mount application code, install npm packages, install operating-system packages, download Chromium, or build an image at startup.
- The container runs as non-root, applies pending Prisma migrations before serving, starts the standalone Next.js process as PID 1, becomes healthy only when PostgreSQL is ready, and can launch its bundled Chromium for Kyobo detail pages.
- PostgreSQL data and downloaded covers survive application image upgrades and container recreation. Runtime secrets, administrator credentials, local data, and development artifacts are absent from the build context and image.
- The release helper refuses unsafe or inconsistent state, never exposes the Forgejo token, preserves immutable semantic versions, and moves `latest` only after the versioned image, Git tag, and Forgejo release are verified.
- Deployment, upgrade, rollback, certificate trust, first-administrator setup, local development, and maintainer publication are documented, and all static checks, tests, production build, built-image smoke checks, and available cross-platform/registry checks pass.

## Out of scope

- Do not add Forgejo Actions or another CI/CD service, automate deployment to a specific server, publish Docker image archives as release assets, or commit registry credentials and production secrets.
- Do not change application features, database models, authentication behavior, Kyobo scraping behavior, or backup formats except for packaging changes strictly required to build and start the production image.
- Do not configure the host Docker daemon, install Docker/binfmt, alter the `git.lan` certificate, create Forgejo tokens, or weaken TLS verification from repository code; those remain operator prerequisites.
